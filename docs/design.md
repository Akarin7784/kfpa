# KFPA —— 详细架构设计（Design Document）

> **KFPA: Knowledge-First Pipeline Architecture** —— 知识优先的流水线式多智能体软件生产架构。
> 核心定位：**日式详细设计（詳細設計）开发方式的 AI 化** —— 人类出原始详细设计，AI 负责设计辅助、转译与零思考执行。

- 版本：v2.0
- 状态：设计定稿（纸面工程完整，待工程实现）
- 配套文档：[设计规格 spec.md](spec.md) · [技术选型 tech-stack.md](tech-stack.md) · [架构图 diagrams/architecture-v2.html](../diagrams/architecture-v2.html) · [模型配置 ../config/models.yaml](../config/models.yaml)

## 1. 设计哲学

### 1.1 一句话定义

把日企验证几十年的详细设计开发方式原样搬给 AI：

| 日企角色 | KFPA 对应 | 说明 |
|---|---|---|
| 設計者（写詳細設計書的人） | **人类设计者** | 原始设计、设计变更、質問票批量确认 |
| 設計補助/課長（审设计的人） | **主BOT**（旗舰挡） | 设计辅助、转译、質問票生成、对抗性评审 |
| 作業員（按设计书实现的担当） | **Flash 执行器**（执行挡） | 零思考、纯编码、不写测试 |
| QA 票 / 設計変更管理 | **質問票机制 / 影响分析** | 本文 §5 |

### 1.2 失败经济学（本架构的地基）

传统软件工程返工贵，因为返工烧**人月**；KFPA 把返工成本压缩为 **token**。由此：

- 流程最优策略从"一次做对"（瀑布思维）变为"快速试错"（进化思维）；
- 串行小步滚动、失败回滚重来，在"人月贵"的世界低效，在"token 便宜"的世界最优；
- **前提**：失败原因必须回灌下一次任务包。带反馈的重试是收敛的，不带反馈的重试是掷骰子；
- **稀缺资源不是 token，是人类的确认带宽**——所有人工卡点必须攒批异步处理。

### 1.3 两种使用模式（同一套基础设施）

- **正经模式**：人类详细设计 + 質問票 + 全流程纪律。为"错了不止烧 token，还要赔钱赔信誉"的系统服务。
- **懒人模式**：全自动放手，AI 连设计一起包，错误成本 = token。其输出上限由质量门禁与知识库质量决定——**正经模式修路，懒人模式开车**。

### 1.4 适用域

- ✅ 适合：需求稳定、规格明确的企业系统 / CRUD 密集型 / 迁移重构 / 维护保守（详细设计方式的经典主场）
- ❌ 不适合：需求边做边长的探索型产品（需求都说不清，详细设计个寂寞）

## 2. 角色与职责

| 角色 | 职责 | 明确不做的事 |
|---|---|---|
| **人类设计者** | 原始详细设计、设计变更、質問票批量确认、每周批量承认小变更 | 不写代码、不逐条实时响应 |
| **主BOT**（旗舰挡） | ① 设计辅助：起草草案 / 生成質問票 / 对抗性评审 ② 设计转译：编码任务包生成 ③ 调度与异常：分级重试 / 变更影响分析 / 重规划 ④ 反馈回灌：失败分析入库 | 不擅自修改人的设计决策 |
| **功能BOT**（旗舰/中档） | 设计功能N + 审核第 N-1 轮提交的代码 | — |
| **Flash 执行器**（执行挡） | 纯编码、快速修复、局部优化 | **不写测试**、不做设计决策 |
| **质量层** | 集成/回归/安全测试、审查聚合、三态门禁 | 测试从设计规约生成，与实现解耦 |

**模型绑定铁律**：代码中只允许出现角色名（`ARCHITECT` / `REVIEWER` / `FLASH` / `EMBEDDING`），严禁出现模型字符串。所有模型绑定收敛于 `config/models.yaml`，换模型 = 改配置 + reload，零代码。

## 3. 分层架构

```
┌─────────────────────────────────────────────────┐
│                人类设计者                          │
│     原始详细设计 · 设计变更 · 質問票批量确认          │
└─────────────────────────────────────────────────┘
        ↑①質問票上呈                ↓②确认放行
┌─────────────────────────────────────────────────┐
│        主BOT（旗舰挡 · 控制平面）                    │
│  ①设计辅助  ②设计转译  ③调度与异常  ④反馈回灌        │
└─────────────────────────────────────────────────┘
   ↑↓ 知识检索              ↑↓ 记忆读写        ↓ 任务包/调度
┌──────────────────┐    ┌──────────────────┐
│ 知识与组件库        │    │ 项目记忆与状态库     │
│ RAG+规则引擎       │    │ ADR·任务状态·質問票台账│
└──────────────────┘    └──────────────────┘
┌─────────────────────────────────────────────────┐
│     功能开发流水线（串行滚动 · 每轮先审核上一轮提交）      │
│  功能N BOT → 编码任务包 → Flash 执行器 → 代码实现      │
└─────────────────────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────┐
│  验证与质量控制层（测试从设计规约生成，与实现解耦）        │
│  集成测试 → 审查聚合 → 质量门禁（三态）                │
│  通过→版本管理 │ 需修复→自主重试 │ 阻塞→升级主BOT ③     │
└─────────────────────────────────────────────────┘
      ┌────────────── 维护轻量通道（小变更快车道）──────────┐
      │ 小变更 → 影响分析 → 微型规格 → 人批量承认 → Flash 直跑 │
      └──────────────────────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────┐
│  产物与版本管理：Git 按轮快照（代码+任务包+测试绑定）     │
└─────────────────────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────┐
│  知识沉淀（带闸门）：执行结果 → 沉淀闸门 → 隔离区 → 知识库│
│  失败记录 → 回避模式清单；不合格沉淀直接丢弃              │
└─────────────────────────────────────────────────┘
```

完整可视化版本：[diagrams/architecture-v2.html](../diagrams/architecture-v2.html)

### 3.1 各层要点

1. **人类设计者（上游）**：人在画布上游，做杠杆率最高的事。设计书里的歧义由主BOT 在转译时发现并开票，而不是被 Flash 固化成代码。
2. **主BOT（控制平面）**：四职能缺一不可——设计辅助 / 设计转译 / 调度与异常 / 反馈回灌。第一交付物是"你这份设计我没看懂的地方列表"（質問票），不是任务包。
3. **知识平面**：知识与组件库（RAG+规则引擎）供设计与转译检索；项目记忆与状态库存 ADR、任务状态、質問票台账、失败记录与回避模式清单。
4. **流水线（执行平面）**：串行滚动，轮首评审上一轮提交 → 返工上限 = 一轮在途工作量。Flash 不写测试——测试来自设计规约，规约与实现解耦。
5. **质量平面**：三态门禁判据必须量化（覆盖率门槛、审查仲裁规则），禁止"模型拍脑袋"。
6. **产物平面**：每轮快照绑定（代码+任务包+测试结果），轮次打标，回滚一键完成。
7. **沉淀平面**：见 §5.5。

## 4. 轮次生命周期

```
① 人提交原始设计（或设计变更）
② 主BOT 转译 → 产出質問票清单（歧义报告）上呈人
③ 人确认后放行 → 主BOT 生成编码任务包
④ 功能N BOT：设计功能N + 审核第 N-1 轮代码
⑤ Flash 执行器编码
⑥ 质量门禁三态判定
⑦ 出口处理（通过/需修复/阻塞，见 §5.3）
⑧ 执行结果 → 项目记忆 + 沉淀闸门
```

**硬规则**：存在未关闭的高影响質問票时，不得生成任务包、不得开跑。

## 5. 关键机制规格

### 5.1 質問票（QA 票）机制

日企实现担当遇歧义提 QA 票，是详细设计方式运转的隐形安全阀。Flash 不会提问，因此该机制前移至主BOT：

- **生成时机**：主BOT 转译设计时，凡遇无法唯一确定解释的表述即开票
- **票面结构**：票号 / 位置（设计书章节）/ 两种可能解释 / 主BOT 倾向 / 影响面
- **处理方式**：攒批异步（不逐条实时，保护人的确认带宽），确认结果写入質問票台账
- **双重保险**：既防"人的设计含糊"，也防"主模型推理不够细"——模型没想明白的地方以票的形式暴露给人

### 5.2 编码任务包强制结构（全系统最贵资产）

Flash 越笨，规约必须越精确。六段式模板（Jinja2 渲染）：

1. **目标描述**：做什么，一句话
2. **验收标准**：可测试的断言，逐条列出
3. **边界条件清单**：输入域、异常流、并发/幂等要求
4. **接口契约**：签名、入参出参、错误码
5. **禁止事项**：不许动的模块、不许引入的依赖、不许的模式
6. **回灌区**：上一轮失败原因与规避要求（若有的话）

> 含糊的任务包会被零思考执行器高速实现成确定性的错误。

### 5.3 分级重试与三态出口

| 门禁结果 | 处理 | 是否惊动人 |
|---|---|---|
| 通过 | 提交版本管理（按轮快照） | 否 |
| 需修复 | Flash 自主重试，**失败原因必须回灌新任务包**；同类失败 ≥2 次自动升级 | 否（升级时是） |
| 阻塞 | 升级主BOT → 变更影响分析 → 重规划（改需求/改任务） | 是 |

### 5.4 变更影响分析（重规划前置）

主BOT 改任务之前必须先算：改这个任务会炸掉多少在途工作？项目记忆库中的任务状态图就是依赖图。不做影响分析就拍脑袋改，等于用一轮浪费换另一轮浪费。

### 5.5 知识沉淀闸门（防知识库中毒）

- 沉淀候选先过：**置信度门槛 + 人工抽检**（抽样率随该来源历史准确率动态调整）
- 新知识先进**待验证隔离区**，被 ≥1 个后续轮次成功复用后才转正
- **失败记录单独沉淀为回避模式清单**，下一轮任务包显式规避——负知识同样值钱
- 不合格沉淀直接丢弃，不进知识库

### 5.6 维护轻量通道（快车道）

软件真实成本两八开：两成开发，八成保守运用。最不需要人类智慧的活占需求的大头。

- **判据**（主BOT 影响分析自动给出）：不新增/不修改接口契约、不改数据模型、波及面 ≤ 1 个模块
- **流程**：小变更 → 主BOT 微型规格 → 人每周攒批承认 → Flash 直跑
- 触碰设计边界的变更一律升级回完整设计回合

## 6. 技术选型（开源优先 · 少写代码）

| 组件 | 选型 | 白送的能力 |
|---|---|---|
| 模型分级路由 | LiteLLM | 旗舰/Flash 一地址切换，token 记账自带 |
| Flash 执行器 | Aider | 每次修改自动 git commit——轮次快照和一键回滚白送 |
| 流水线状态机 | LangGraph | checkpoint=项目记忆持久化，interrupt=質問票/人确认 |
| 知识库 RAG | Dify 自托管 | 设计书/踩坑记录喂进去就有 API 可查 |
| 状态库 | PostgreSQL | 任务状态/質問票台账/失败记录全是表 |
| 审查聚合 | PR-Agent（Qodo 开源版） | 多维代码评审现成 |
| token 账本 | Langfuse | 每轮烧钱曲线仪表盘 |
| 質問票界面 | Streamlit | 台账+批量确认约 100 行 |

自写胶水约 300–500 行：LangGraph 图定义、Jinja2 任务包模板、门禁三态判定脚本。

详见 [tech-stack.md](tech-stack.md)（含懒人版/正经版两种部署形态与风险清单）。

## 7. 模型配置与债务管理

- 当前：全栈 DeepSeek-V4.1-Flash 两挡位（决策开思考 / 执行关思考），单 API 少管 key
- 已知妥协：**同源盲区**——设计者、执行者、评审者共享训练偏差。缓解：REVIEWER 位强制 `fresh_context: true` + 独立角色 prompt；接入异构 API 后优先换评审位（裁判不能和运动员同权重）
- 换挡信号（Langfuse 可观测）：
  1. 質問票数量异常（提得少但返工多——该问的没问出来）
  2. 同类失败重试 ≥2 次（回灌后仍学不会）
  3. Aider diff 应用成功率下滑（格式都维持不住时，别让它写设计）

详见 [../config/models.yaml](../config/models.yaml)。

## 8. 路线图

- [ ] **P0 懒人版**：LiteLLM + Aider + SQLite + Dify，一天跑通第一轮（设计→質問票→确认→编码→门禁）
- [ ] **P1 正经版**：PostgreSQL + Langfuse + PR-Agent + Streamlit 質問票台账
- [ ] **P2 评审位异构化**：接入第二个模型 API，消化同源盲区债务
- [ ] **P3 快车道 + 沉淀闸门全量落地**，验证八成维护长尾的消化能力

## 9. 非目标（Non-Goals)

- 不做并行多功能流水线（串行的返工上限是可计算的，并行的返工是级联的）
- 不做无人工确认的全自动生产交付（懒人模式仅限错误成本=token 的场景）
- 不自研智能体框架（每个想少写代码的人的第一死法）
